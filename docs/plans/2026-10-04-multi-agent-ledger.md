## Rulings

Spike findings (spec §3 "Spike findings") that contradict an assumption of the plan, with the task each one changes:

- **F7 → Task 2 (hooks.json form).** Neither Codex nor Copilot CLI runs the exec form `"command":"bash","args":[…]` that `plugins/harness/hooks/hooks.json` uses today. Codex fails open (the guard is off), and Copilot fails closed (every matched tool is denied). Task 2 switches all five hook entries to the string form `"command": "bash \"${CLAUDE_PLUGIN_ROOT}/scripts/<name>.sh\""` with no `args`, test-first. In `tests/manifest.sh`, `h-exec-form` becomes `h-string-form`: no hook has `args`, and every command matches `^bash "\$\{CLAUDE_PLUGIN_ROOT\}/scripts/[a-z-]+\.sh"$`. `h-has-scripts`, the script-existence loop and `h-plugin-root` read `.command` instead of `.args[]`. This reverses the exec-form choice of the 0.1.0 design (§ hooks of `docs/specs/2026-09-24-agentic-harness-design.md`, `CHANGELOG.md`), so the 0.5.0 changelog says why. The double quotes keep a path with spaces in one argument. Confirm by hand that Claude Code still runs the hooks (`claude --plugin-dir plugins/harness`, a blocked `rm -rf` in a scratch repo) and record the result in this ledger.
- **F4 → Task 2 (Copilot `Edit` input is a string).** Copilot reports its `apply_patch` as `tool_name: "Edit"` with `tool_input` a JSON string (the patch text), not an object. In `guard.sh`, the patch body filter becomes `.tool_input | if type == "string" then . else (.command // .input // "") end`, and the `file-path-keys` filter becomes `(.tool_input | objects | (.file_path // .notebook_path // .path)) // ""`, so that a string `tool_input` never makes `jq` fail. In `tests/hooks/run.sh`, add a payload type `cpatch:<Tool>:<printf %b text>` that sends `{tool_name:$t, tool_input:$c}` with `$c` a string. Add cases: `g-cop-04` `block:env-file` `cpatch:Edit:*** Begin Patch\n*** Add File: .env\n+X=1\n*** End Patch`; `g-cop-05` `pass` with `*** Add File: src/app.ts`; `g-cop-06` `block:bad-input` `cpatch:Edit:not a patch` (a string `tool_input` that is not a patch cannot be checked). `cfile:` keeps `tool_input.path`, which is Copilot's `Read` (`view`) shape.
- **F2/F4 → Task 3 (paths absolute or relative).** Codex's model wrote an absolute path after `*** Update File:`, while Copilot wrote a relative one. `lint-on-edit.sh` reads patch paths from either `tool_input` shape, using the same filter as Task 2. It turns an absolute path under `cwd` into the `<rel>` it reports and lints. Add a lifecycle case with an absolute `*** Update File:` path. Copilot's PostToolUse carries `tool_result` rather than `tool_response`, so the `.tool_response.filePath` fallback never applies there.
- **F6 → Task 3 (Copilot PostToolUse output).** Copilot ignores nested `hookSpecificOutput.additionalContext` and honours `decision: "block"`. The block hides the tool output behind `Tool result blocked: R`, marks the edit failed although it was applied, and drops any `additionalContext`. Only top-level `additionalContext` reaches the model as context. Change: when the PostToolUse payload has `tool_result`, which is Copilot's shape (F4) and the "signal" spec §5.2 asks for, print `{"additionalContext":R}` alone. Otherwise print the planned `{"decision":"block","reason":R,"hookSpecificOutput":{…,"additionalContext":R}}`. Add a lifecycle case with a Copilot-shaped payload that asserts `.additionalContext == R and (has("decision") | not)`.
- **F10 → Tasks 9, 10, 11 (Copilot dispatch).** The plugin agents' `model: sonnet` and `model: opus` are literal ids in Copilot, so dispatch through `task` fails unless the call passes a model. Every Copilot dispatch therefore passes `model` and `reasoning_effort` from the Copilot column of `docs/harness/models.md`. Task 9 resolves `<F10 …>` to "and pass the model …" and adds "without `model` the dispatch fails". Task 10 resolves `<F10 …>` to "`task` with `model` and `reasoning_effort`; the intermediate review uses `harness:reviewer` with the fast model". Task 11's Copilot row reads `task(agent_type: "harness:implementer" | "harness:reviewer", model: …, reasoning_effort: …, mode: "background")`, with follow-ups through `write_agent {agent_id, message}` and then `read_agent {agent_id, wait: true}` (a `sync` agent rejects `write_agent`).
- **F9 → Tasks 6, 11, 12 (Codex dispatch).** Codex can pass `model` and `reasoning_effort` per `spawn_agent`, so the plan's premise that it cannot is wrong. Task 6 still pins models in `.codex/agents/*.toml` and keeps `harness-reviewer-intermediate`: a pinned definition does not depend on the main agent passing the model. Task 6 uses `STRONG_MODEL=gpt-6-luna STRONG_EFFORT=high FAST_MODEL=gpt-6-luna FAST_EFFORT=medium` (F12). A spawn without `fork_turns` forks the parent's context, which breaks "the context that implemented something never reviews it". Task 11's Codex row is therefore `spawn_agent {agent_type: "harness-reviewer", task_name, message, fork_turns: "none"}`, with follow-ups through `followup_task {target: <task_name>, message}` and then `wait_agent`. `fork_turns: "none"` was seen only in the binary's argument strings, so Task 12's manual Codex smoke confirms it gives a fresh context and records the result here.
- **F12 → Task 10 (model ids).** Codex: strong and fast are both `gpt-6-luna`, told apart by effort (`high` and `medium`), because the account lists no larger current model. Copilot: strong `claude-opus-5.5`, fast `claude-sonnet-5.5`. These are documented ids but unusable on the PO's account, which accepts only `--model auto`, while `task` accepts its own list. The Copilot section of `models.md` adds: "If `task` answers that a model is not available, it lists the available ones; use the closest one from that list." Valid effort values: Codex low|medium|high|xhigh|max; Copilot none|minimal|low|medium|high|xhigh|max.
- **F8 → Tasks 8, 12 (Codex hook trust).** Codex skips the plugin's hooks, silently in `codex exec`, until the user has reviewed and trusted them. The "Codex specifics" section (Task 8) and the README "Agents" section (Task 12) add: "Until you trust the harness hooks in Codex, the guard does not run." The skill names are `harness:<skill>`, so `<F8 …>` becomes `$harness:workflow`, `$harness:design` and `$harness:execute`.
- **F11 → Tasks 9, 11, 12 (UNCONFIRMED → skill route).** `/opsx:*` could not be checked interactively. Under `-p` the command is not expanded. Following Ruling R2 of the session record, the Copilot rows use the skills `openspec-propose`, `openspec-archive-change` and `openspec-update-change`. Copilot loads `openspec-*` skills from `.claude/skills` and `.agents/skills`.

Findings that confirm the plan and need no change: F1 (`Bash`, so Task 5 adds no `cshell:` cases), F3 (Claude's shape, so `copilot-bash:` is not needed), F5 (nested `permissionDecision` works, so Task 5 Step 2 is skipped), F13 (the keys load and `execpolicy check` prints JSON; project config and rules load only for projects trusted in `~/.codex/config.toml`), F14 (Task 9 adds the "may show the rules twice" line), F15 (Copilot CLI 1.0.91, Codex CLI 0.160.0).
