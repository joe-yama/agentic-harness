## Rulings

Spike findings (spec §3 "Spike findings") that contradict an assumption of the plan, with the task each one changes:

- **F7 → Task 2 (hooks.json form).** Neither Codex nor Copilot CLI runs the exec form `"command":"bash","args":[…]` that `plugins/harness/hooks/hooks.json` uses today. Codex fails open (the guard is off), and Copilot fails closed (every matched tool is denied). Task 2 switches all five hook entries to the string form `"command": "bash \"${CLAUDE_PLUGIN_ROOT}/scripts/<name>.sh\""` with no `args`, test-first. In `tests/manifest.sh`, `h-exec-form` becomes `h-string-form`: no hook has `args`, and every command matches `^bash "\$\{CLAUDE_PLUGIN_ROOT\}/scripts/[a-z-]+\.sh"$`. `h-has-scripts`, the script-existence loop and `h-plugin-root` read `.command` instead of `.args[]`. This reverses the exec-form choice of the 0.1.0 design (§ hooks of `docs/specs/2026-09-24-agentic-harness-design.md`, `CHANGELOG.md`), so the 0.5.0 changelog says why. The double quotes keep a path with spaces in one argument. Task 2's implementer checks by hand that Claude Code still runs the hooks: `claude --plugin-dir plugins/harness` in a scratch repository, where `rm -rf ./x` must be refused by the guard. The implementer records the command and the refusal in its report.
- **F4 → Task 2 (Copilot file tools).** Copilot reports its `apply_patch` as `tool_name: "Edit"` with `tool_input` a JSON string (the patch text), not an object. `view` arrives as `Read` with the object `{path}`, so Read payloads are always objects. The hook-facing shape of a Copilot `create` tool is UNCONFIRMED: no model this account can use exposes `create`. An older session logged an internal `create` call as the object `{path, file_text}`. `guard.sh` reads a file-tool payload in this order:
  1. `tool_input` is an object (Claude's tools, Copilot `Read`, and a Copilot `create`/`Write` if it sends `{path, file_text}`): `check_path` on `.file_path // .notebook_path // .path`, as today. The filter becomes `(.tool_input | objects | (.file_path // .notebook_path // .path)) // ""`, so a string `tool_input` never makes `jq` fail.
  2. `tool_input` is a string holding `*** Begin Patch` (Copilot `Edit`, possibly `create`): `check_path` on every line `patch_paths` prints. The body filter becomes `.tool_input | if type == "string" then . else (.command // .input // "") end`.
  3. `tool_input` is a string that parses as a JSON object (a double-encoded object): `check_path` on `(fromjson? | objects | (.file_path // .path)) // ""`.
  4. Any other string (no patch header and no path key) is `bad-input`: guard cannot tell what the tool writes.

  In `tests/hooks/run.sh`, add a payload type `cpatch:<Tool>:<printf %b text>` that sends `{tool_name:$t, tool_input:$c}` with `$c` a string. Add these cases:
  - `g-cop-04` `block:env-file` `cpatch:Edit:*** Begin Patch\n*** Add File: .env\n+X=1\n*** End Patch`
  - `g-cop-05` `pass` with `*** Add File: src/app.ts`
  - `g-cop-06` `block:env-file` `cpatch:Write:{"path":".env","file_text":"X=1"}`
  - `g-cop-07` `block:env-file` `cfile:Write:.env`
  - `g-cop-08` `block:bad-input` `cpatch:Write:hello`

  `cfile:` keeps `tool_input.path`. Task 12's Copilot smoke test then creates a file with a model that has `create`, if the account offers one. If `create` is refused as `bad-input` or reaches hooks in another shape, Task 12 records the payload here and fixes `guard.sh` before the PR.
- **F2/F4 → Task 3 (paths absolute or relative).** Codex's model wrote an absolute path after `*** Update File:`, while Copilot wrote a relative one. `lint-on-edit.sh` reads patch paths from either `tool_input` shape, using the same filter as Task 2. It turns an absolute path under `cwd` into the `<rel>` it reports and lints. Add a lifecycle case with an absolute `*** Update File:` path. Copilot's PostToolUse carries `tool_result` rather than `tool_response`, so the `.tool_response.filePath` fallback never applies there.
- **F6 → Task 3 (Copilot PostToolUse output).** Copilot ignores nested `hookSpecificOutput.additionalContext` and honours `decision: "block"`. The block hides the tool output behind `Tool result blocked: R`, marks the edit failed although it was applied, and drops any `additionalContext`. Only top-level `additionalContext` reaches the model as context. Change: when the PostToolUse payload has `tool_result`, which is Copilot's shape (F4) and the "signal" spec §5.2 asks for, print `{"additionalContext":R}` alone. Otherwise print the planned `{"decision":"block","reason":R,"hookSpecificOutput":{…,"additionalContext":R}}`. Add a lifecycle case with a Copilot-shaped payload that asserts `.additionalContext == R and (has("decision") | not)`.
- **F10 → Tasks 9, 10, 11 (Copilot dispatch).** The plugin agents' `model: sonnet` and `model: opus` are literal ids in Copilot, so dispatch through `task` fails unless the call passes a model. Every Copilot dispatch therefore passes `model` and `reasoning_effort` from the Copilot column of `docs/harness/models.md`. When that id is not available on the account, the dispatch passes the fallback `gpt-5.6-luna` (F12), which `task` accepted in the F10 probe. Task 9 resolves `<F10 …>` to "and pass the model …" and adds "without `model` the dispatch fails". Task 10 resolves `<F10 …>` to "`task` with `model` and `reasoning_effort`; the intermediate review uses `harness:reviewer` with the fast model". Task 11's Copilot row reads `task(agent_type: "harness:implementer" | "harness:reviewer", model: …, reasoning_effort: …, mode: "background")`, with follow-ups through `write_agent {agent_id, message}` and then `read_agent {agent_id, wait: true}` (a `sync` agent rejects `write_agent`).
- **F9 → Tasks 6, 11, 12 (Codex dispatch).** Codex can pass `model` and `reasoning_effort` per `spawn_agent`, so the plan's premise that it cannot is wrong. Task 6 still pins models in `.codex/agents/*.toml` and keeps `harness-reviewer-intermediate`: a pinned definition does not depend on the main agent passing the model. Task 6 uses `STRONG_MODEL=gpt-6-luna STRONG_EFFORT=high FAST_MODEL=gpt-6-luna FAST_EFFORT=medium` (F12). A spawn without `fork_turns` forks the parent's context, which breaks "the context that implemented something never reviews it". Task 11's Codex row is therefore `spawn_agent {agent_type: "harness-reviewer", task_name, message, fork_turns: "none"}`, with follow-ups through `followup_task {target: <task_name>, message}` and then `wait_agent`. `fork_turns: "none"` is UNVERIFIED: it comes from strings in the Codex binary, and no spawn used it. The test spawns `harness-reviewer` with `fork_turns: "none"` and checks that the child's `session_meta` has no `forked_from_id` and that the child cannot quote the parent's earlier messages. The result goes in this ledger. If it fails, Task 11's Codex row must say, before the PR, how to start a subagent without the parent's context (another `fork_turns` value or argument that the smoke test shows works), or state plainly that Codex subagents inherit the parent's context. In the second case, the final review runs in a separate `codex exec` session.
- **F12 → Task 10 (model ids).** Codex: strong and fast are both `gpt-6-luna`, told apart by effort (`high` and `medium`), because the account lists no larger current model. Copilot: strong `claude-opus-5.5`, fast `claude-sonnet-5.5`. These are documented ids but unusable on the PO's account, which accepts only `--model auto`, while `task` accepts its own list. Task 10 writes `gpt-5.6-luna` into the Copilot section of `models.md` as the fallback for both roles. `task` accepted it in the F10 probe (`task {"agent_type":"cap:probe","model":"gpt-5.6-luna",…}` → `ok`). Valid effort values: Codex low|medium|high|xhigh|max; Copilot none|minimal|low|medium|high|xhigh|max.

The "Codex specifics" section (Task 8) and the README "Agents" section (Task 12) add: "Until you trust the harness hooks in Codex, the guard does not run." The skill names are `harness:<skill>`, so `<F8 …>` becomes `$harness:workflow`, `$harness:design` and `$harness:execute`.

## Deviations

Departures from the spec that the branch ships with:

- Spec §5.1 puts a `hook_input` function in `lib/parse.sh` for all four scripts to read the hook payload. It was not built: the scripts read the payload with inline `jq` filters (the per-agent shapes are handled inline in `guard.sh` and `lint-on-edit.sh`), which the payload-shape cases in `tests/hooks/cases.tsv` and `tests/hooks/lifecycle.sh` cover.
- `lint-on-edit` sends the lint report in both `reason` and `hookSpecificOutput.additionalContext` for Claude Code and Codex. Sending it once is deferred.
- The PR-template line for the agent and model of each stage (M7) is deferred; `harness:workflow` ("Mixed agents") asks the PR evidence to name them.
